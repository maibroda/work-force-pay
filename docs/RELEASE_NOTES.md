## Not yet merged (branch `paying-bank-files`, migration `20261105150000_paying_banks`)

- **Bank payment files for the bank the client pays from** (a bank-file module change, rule 13). A **paying bank** is data: its own versioned list of bank codes, its own upload layout, and the company's account at it. First Bank is loaded with its six-column template and the list it supplied; Access Bank's list is loaded but **its upload template was not supplied, so no Access file can be made yet**. A bank's codes are valid only on its own list (Stanbic IBTC is 039 for Access and 221 for First Bank), so each employee's bank is matched only against the chosen bank's list. Entries that could send money to the wrong place (a test bank, a code shared by two banks, a bank under two codes, a code that may have lost a leading zero) are **blocked on import** and listed as a problem, never put in a file: 6 on Access's list and 14 on First Bank's, to be confirmed with the banks. A newer list becomes a new version; each file records the bank, the list version and its headers. The general file is unchanged when no paying bank is chosen. New page: Payments > Paying Banks. Reversible migration (three new tables, three nullable columns). Tests: 19 unit and 11 integration.

## Merged: failed-login audit (#79, branch `failed-login-audit`)

- **The two-factor step can no longer be guessed without limit** (a change to sign-in, approved by the founder). Before, any number of wrong codes was accepted (nothing counted, locked or logged them), and a correct password reset the failure count, so wrong guesses could be mixed with right passwords and never reach the lock. Now **a wrong code counts on the same counter as a wrong password: five in total lock the account for 15 minutes**, and a locked account refuses even the right code. For an account with two-factor on, **a correct password no longer clears the count; only the whole sign-in succeeding does** (an account without two-factor is unchanged). The message for a wrong code is still "Incorrect code.". The count is raised in one database step, so many guesses sent at the same moment cannot read the same old number.
- **Failed sign-ins and related failures are now in the audit log** (rule 5), in the account's own organization, with the address and the browser, and never the password, code, reset token or sign-in challenge. New actions: `LOGIN_FAILED` (reasons `WRONG_PASSWORD`, `ACCOUNT_LOCKED`, `ACCOUNT_INACTIVE`), `TOTP_FAILED`, `PASSWORD_RESET_REQUESTED`, `PASSWORD_RESET_FAILED` (`TOKEN_USED`, `TOKEN_EXPIRED`), `PASSWORD_CHANGE_FAILED`, `TOTP_DISABLE_FAILED`; `ACCOUNT_LOCKED` now says whether passwords or codes caused it. Attempts on a locked or switched-off account are written at most once every five minutes. The audit report has a **Show: Security events** filter. An email with **no account** goes to the application log only, as a keyed hash plus the address (never the email, because people type passwords in the email box). The replies to the person signing in are unchanged. **Not done:** a limit by IP address (waits for the host decision); a limit on wrong current passwords or codes on the change-password and turn-off-two-factor screens. No pay figure changes; no migration; no new dependency.

## Previously not yet merged (branch `verified-settings-gate`, now #77)

- **Payroll is blocked while a required statutory rule is unverified** (rule 3). For a **production client** (a client of the bureau whose engagement is **ACTIVE**), the PAYE, pension and employer-contribution rules in force for the period must each be exactly what **HR and Finance both signed** in the bureau's Statutory Rule Library, or the payroll is stopped. The check is made when a payroll is calculated, when a supplementary payroll is created, and when a payroll is **submitted, approved and locked**, so a rule changed after the calculation cannot slip through. It checks the rule's content against what was signed, so a rate changed directly in the database after sign-off is caught; how the rule reached the client (published, or copied when it was onboarded) does not matter. A rule the bureau is paying on that was **never put through the library** (a "baseline") counts as unverified, which matches the launch checklist. **There is no override**: the message names the rule and says to verify it in the library. **Every block is written to the audit log** (who tried, which step, which rule, why). Clients still being onboarded, the bureau's own organization and organizations that are not bureau clients are not stopped, but the payroll page now tells a person plainly which rules are not yet verified, and, when all are, who verified them and when. **No pay figure changes** (all 401 seeded figures are identical). The demo client now goes through the real propose, verify and publish steps and goes live, so it is gated and passes for the right reason. **Before the first real client goes ACTIVE, the bureau must run its current PAYE, pension and employer-contribution rules through the library once.** No migration.

See `docs/rules-conformity.md` for the full list against the project rules, and `docs/threeroots-gap-analysis.md` for the product gaps. The largest: money is calculated in floating-point numbers, statutory rules have no "verified" gate on a payroll run, there are no golden tests or feature flags, field encryption is unbuilt, and migrations can't be reversed.
