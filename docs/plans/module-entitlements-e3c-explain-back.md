# E3c explain-back note: the scheduled jobs respect the module switch (built; nothing turned on)

Written 2026-11-03. For the founder. This touches access control (what runs for which company), so it is a critical change under `CLAUDE.md`. **While every module is OFF, which is how it starts, every job runs for every company exactly as before.** I did not turn any module on, and I will not: that is your decision.

1. **The gap this closes.** The guards from E3a cover pages, server actions and API routes, but the scheduled jobs (`/api/cron/*`) have no signed-in person: each runs for every company. Without this, enforcing a module would still let its job send HR digests, post recurring journals or score CRM accounts for a company that did not buy it.
2. **What it does.** One shared function, `entitledOrgs(companies, job)`, answers "which of these companies may this job run for?". It looks up the job's module (from the same declarations as everything else), then the switch: OFF means all of them; REPORT means all of them, with one log line for each company that would have been skipped (module, job and company id, nothing personal); ENFORCE means only companies that have the module today (from their subscription, so an ended module does not count). A company with no subscription counts as having the core only. An unknown job name throws, so a typo can never let a job run for everyone unchecked.
3. **Where it is used (9 services, all 12 jobs covered).** HR digest, data retention (HR); journal reversals and recurring journals (Accounting); payroll reminders (Payroll); and the four CRM jobs: sales digests, health scores, case SLA clocks and renewals, and automation (queuing the no-activity rules, and carrying out a queued run, which is cancelled with a plain note if the company no longer has the module). The three audit-log jobs are the core and never held back.
3a. **The three jobs that were guesses are confirmed (the founder, 2026-11-03):** journal reversals and recurring journals are Accounting, and payroll reminders are Payroll (the ledger postings belong to Accounting; the reminders belong to Payroll). They are now held back like the rest, and a test pins both the module and that they are no longer guesses. Only the three audit-log jobs remain core.
4. **What could go wrong.** (a) A company enforced out of a module still has its data; a job skipping it just stops sending or posting for it, and starts again when the module returns. (b) CRM automation that is queued at the moment a company stops having the module is cancelled when it falls due, not run. (c) An event hook that queues automation when a deal changes is not itself filtered (it would log on every deal change in REPORT mode); the queued run is, so nothing is carried out. (d) The check costs one lookup per job run while the module is OFF, and one subscription lookup per company when it is not.
5. **Worked example.** Platform staff set HR to ENFORCE. At 06:00 the HR digest job runs: Company A (bought HR) gets its digest; Company B (payroll only) is skipped with no result and no email, and nothing is written to its records. In REPORT mode instead, B would also get its digest and the log would say, once, that HR would have been refused for B.
6. **Which tests prove it.** `tests/integration/entitlements-jobs.test.ts`: OFF runs everything; ENFORCE keeps only companies that bought it, and treats one with no subscription as the core; REPORT runs everything and names only the company it would have skipped; the core jobs are never held back; the three confirmed jobs are held back by Accounting and Payroll; an unknown job throws; the HR digest and data-retention jobs really skip a company that did not buy HR; and a wiring test that every non-core job asks `entitledOrgs` with its own name in a service it calls.
7. **Honest limits.** The accounting, payroll-reminder and CRM jobs are covered by the wiring test and the shared function, not by an end-to-end run of each job with the switch on. Nothing has been run in a hosted environment, because none exists.
