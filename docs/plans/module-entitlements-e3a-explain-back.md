# E3a explain-back note: the module guards (built, switched off)

Written 2026-11-03. For the founder. This touches access control (every page, server action and API route), so it is a critical change under `CLAUDE.md`. **It changes nothing anyone can see or do today.**

1. **What it does.** Every way into the app now says which module it belongs to (`src/lib/entitlements/entry-modules.ts`: 234 pages, 63 action files, 19 API routes, 12 scheduled jobs). Three guards read that: pages (inside `requirePage`), server actions (inside the one `act` wrapper they all use) and API routes (one line after the sign-in checks). A guard asks one question: *is this module being enforced for this company, and if so, did the company buy it?*
2. **Why nothing changes yet.** The guards look at `ctx.entitlements`, and **nothing sets it** (that is E3b, with the platform switch). With it missing, each guard allows the request. The tests show what the guards would do with it set.
3. **Three states per module.** OFF (nothing checked), REPORT (let it through but write a log line, with the module, the entry and the company, nothing personal), ENFORCE (refuse). A company with no subscription counts as the core only. The core is never refused. "Bureau tools" answer to bureau mode, not to a purchase.
4. **Why the module comes from the entry and not the permission.** Eight permissions are shared between modules (for example `gl.view` opens Accounting, Client billing and Payables pages), so a permission cannot tell which module an action belongs to. The test pins that list; a ninth shared permission fails it until a person looks.
5. **Pages.** The middleware writes the request's own address into a header, overwriting anything the browser sent, and `requirePage` reads it. It is done in the page, not the layout, because a layout is not re-run when someone clicks to another page, which would let a locked page open. A refused person is sent to `/forbidden?module=...`.
6. **Actions.** Each action file now begins `const act = actFor("<its own file>")`, and a test fails if any file does not, or still uses the bare `act`. A refused action does not run, and returns "X is not part of your plan. Ask whoever looks after your account to add it."
7. **A guess can never lock anyone out.** 21 entries are still my reading of a name and are marked unconfirmed; they are held to the core (open to everyone) until you rule on them.
8. **What could go wrong.** (a) A wrong module on an entry would lock people out of something they paid for, once enforcement is on: REPORT mode exists to show this before it bites. (b) The 12 scheduled jobs are declared but not yet guarded: they run for every company, so each must skip companies without its module. That is E3c work, when a module is first enforced. (c) The portal change (it now needs only Payroll) is my recommendation, taken when you said "go"; please confirm.
9. **Worked example (when it is switched on).** A company that bought Payroll Essentials (Core, Payroll) has Inventory set to ENFORCE. Its storekeeper opens `/inventory/ckx12` (page `/inventory/[id]`, module Inventory): sent to the refusal page. Their administrator presses "Add item": the action `inventory.ts` is refused with the plain message and nothing is saved. A company that bought Inventory goes through both. A company in REPORT mode goes through both and two log lines are written.
10. **Which tests prove it.** `tests/unit/entitlements-guard.test.ts` (the decision for every state; address matching; the action wrapper refusing, reporting and passing; and that every action file, API route and page is wired) and `tests/unit/entitlements-entry-points.test.ts` (every entry is declared and none is stale).
11. **Honest limits.** Not yet tested end to end in a running app with enforcement on, because there is no way to turn it on until E3b. Built and tested before any behaviour depends on it.
