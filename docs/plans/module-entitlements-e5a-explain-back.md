# E5a explain-back note: no removal that strands work (built; nothing is enforced yet)

Written 2026-11-03. For the founder. This changes what platform staff, or a bureau for its own clients, can do to a company's subscription, so it touches access control. **Nothing is enforced anywhere yet, so it cannot lock anyone out; it only makes a removal refuse while work is half done.**

1. **What it does.** Before a module is removed from a company (directly, or because a change of plan ends it), the app counts that company's work in progress in the module and refuses or asks for an acknowledgement. It reads only, inside the same database transaction as the change, and only for the company being changed.
2. **Hard blockers (the change is refused until the work is finished or cancelled).** Payroll: a pay run not yet locked or paid; a payment batch still pending. Accounting: a manual journal waiting for approval or posting; a period still being closed. Payables and procurement: a purchase order waiting for approval; a supplier bill that failed its match. Client billing: an invoice waiting for approval.
3. **Soft blockers (reported; the person must acknowledge to go ahead).** Client billing: issued invoices not yet fully paid. CRM: open deals and queued automation. HR: pending leave, open onboarding and exit tasks. They stay readable but can no longer be worked.
4. **Where each rule comes from.** They are the lists I proposed in the E5 plan, taken when you asked me to continue on my recommendations. **They are for you to confirm or change.** The statuses used are the ones the app already has (for example a pay run is "in progress" while it is Draft, Calculated, Pending approval or Approved).
5. **What it never does.** It never deletes or changes any data of the module being removed. A removal only gives the module an end date, as before.
6. **What it does not check.** Stock issued to employees: "still issued" has no definition in the data, so Inventory has no blocker until you define it. Half-written drafts do not block (my recommendation).
7. **What could go wrong.** A list that is too short strands work; too long and a company cannot leave. Each list is a short table in one file with its own test, so changing one is small and visible. A change refused for a hard blocker leaves nothing behind: no history entry, no end date (tested).
8. **Worked example.** A company has Payroll and Accounting. Platform staff try to remove Accounting while one accounting period is soft-closed: refused with "Accounting: 1 accounting period is still being closed. Close or reopen it first." Nothing changes. The company's accountant reopens the period; the same removal now succeeds and the module gets an end date. HR with one pending onboarding task: refused until acknowledged, then removed, and the onboarding task is still there, unchanged.
9. **Which tests prove it.** `tests/integration/entitlements-blockers.test.ts`: each blocker's query and status list is checked exactly (with a stand-in database, so tenancy and statuses cannot drift); every query runs against the real database; the refusals and the acknowledgement path; a change of plan refused with nothing changed; another company's work ignored.
10. **Honest limits.** I wrote the tests first but ran them only after the code existed. The read-only window after removal (E5b) is not built, and a removed module is still refused outright once its switch is ON.

## Addendum, 2026-11-04: the whole HR cycle and Payroll

On the founder's direction that Personnel management, the HR cycle and payroll are the focal point, the lists now cover the cycle end to end. **Hard (refuse):** a final settlement awaiting approval or release (removing Payroll: it is a leaver's last pay, and settlements are processed in Payroll) and an exit awaiting approval (removing HR). **Soft (acknowledge):** a final settlement still being prepared (Payroll); disciplinary records awaiting a decision, appraisals not yet approved, open appraisal cycles and open job requisitions (HR). The earlier lists are unchanged. These are my recommendations, for the founder to confirm. No payroll or leave rule is touched.
