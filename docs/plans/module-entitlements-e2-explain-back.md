# E2 explain-back note: subscriptions

Written 2026-11-03. For the founder. This touches access control (who may change what a company has) and the audit trail, so it is a critical change under `CLAUDE.md`.

1. **What it does.** Every company gets one subscription: a plan (from the catalogue), the list of modules it has with the day each started and, if taken away, the day it ended, two stored limits, and a history. The tables are `Subscription`, `SubscriptionModule`, `SubscriptionEvent` (and an empty `ClientBlueprint` for later). **Nothing in the app reads them to switch anything off yet.** A company with no subscription is not restricted.
2. **Who may change one.** Only platform staff (`SUPER_ADMIN`, who holds `subscription.manage`), and a bureau's administrator (who holds `bureau.manage`) for a company that is one of that bureau's clients. The service checks the client belongs to the bureau the person *works for* (their home organization, even when they are working inside the client). It does not let a bureau change its own subscription or another bureau's client's. A company's own administrator can look (`subscription.view`) and not change.
3. **The trap, and the test.** `COMPANY_ADMIN` is given every permission automatically. If `subscription.manage` were simply added to the list, every company's administrator could give their company every module. So `permissions.ts` removes it from `COMPANY_ADMIN` explicitly, and the first test fails if anyone ever gives it to another role.
4. **Taking a module away.** The module row gets an end date and stays. The service first asks the catalogue what would stop working: if another module the company has needs it (Employee self-service needs Payroll *or* HR; Production pay needs Payroll), it refuses and says so. The core cannot be removed.
5. **Moving plan.** The new plan plus add-ons must hold together (the same catalogue check used for quotes), or nothing changes. Modules not in the new plan are ended; new ones start today; the rest carry on. All inside one database transaction with the subscription row locked, so two people changing the same company cannot interleave.
6. **History.** Every change writes a history entry (what, who, why, and the module keys involved) and an audit-log entry carrying the same keys, never anyone's personal details. A database trigger refuses any update or delete on history entries, so even the application cannot rewrite it.
7. **Existing companies.** The migration gives each company that has none the Custom plan with the 13 modules that are built or partly built, marked "kept from before plans", so nothing a company uses today can stop later. It can run twice without harm. A test runs that exact SQL from the migration file inside a transaction it rolls back.
8. **New companies.** A bureau onboarding a client creates the subscription in the same transaction. **My assumption, for you to confirm: Payroll Essentials by default**; the bureau can change it. If onboarding fails, no subscription is left behind (tested).
9. **What could go wrong.** (a) If someone makes a company by a new route and forgets a subscription, it has none; E3 must refuse to switch enforcement on while any company lacks one (your answer 2), and I will build that check there. (b) Platform staff changes have no second-person approval yet; they are audited and logged but one person can do them. (c) The grandfathered "Custom" plan is a placeholder; someone must review each company. (d) `SUPER_ADMIN` here means platform staff, as elsewhere in the app; I did not check how those accounts are created in production, because no hosting exists yet.
10. **Worked example.** ThreeRoots onboards "Acme Facilities". Acme gets Payroll Essentials: Core and Payroll, both starting today, one history entry "Subscription made", by the person who onboarded it. Later ThreeRoots adds Analytics: refused if Analytics' needs are missing (it needs only the core, so it is added), recorded as "Module added". Acme's own administrator tries to add Accounting: refused, "You do not have permission (subscription.manage)". ThreeRoots tries to remove Payroll while Employee self-service is there and HR is not: refused, "Employee self-service needs one of HR management or Payroll".
11. **Which tests prove it.** `tests/integration/entitlements-subscriptions.test.ts` (permissions trap; who may change across companies and bureaus; refusals with reasons; end-dating with the row kept; history by date; history refused by the database; the migration's grandfathering SQL; ensureSubscription once) and `tests/integration/bureau.test.ts` (onboarding makes the subscription and leaves none behind on failure).
12. **Honest limits.** The tests were written before the code, but I ran them only after it existed, so I did not watch them fail first. The new page was typechecked and is in the smoke test; I have not looked at it in a browser.
